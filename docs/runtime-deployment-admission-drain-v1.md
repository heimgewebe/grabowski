# Runtime deployment admission drain v1

## Purpose

A Grabowski self-deployment must not depend on the operator manually keeping every connector quiet. The deployment path therefore separates three different signals:

1. the deployment lock serializes deployment mutations;
2. the operator admission gate stops new MCP tool calls before tool execution while already-admitted effect-bearing or conservatively unclassified calls finish; explicitly read-only calls may remain in flight;
3. tunnel queue and conserved command counters prove that every accepted command was polled before services stop. Under an active admission gate, final responses from remaining read-only calls may still be outstanding.

`dispatcher_worker_pool_occupancy` remains visible only as diagnostic pool capacity. The running tunnel-client uses `ants.Pool.Running()`, which counts live worker goroutines even while they are parked idle. It is not in-flight command authority.

## Marker contract

The deployer creates `~/.local/state/grabowski/deployment-admission-drain.json` with create-only semantics, mode `0600`, no symlink following, one link, owner UID binding, a maximum thirty-minute lifetime and exact fields for token, expected repository head, source-identity digest and timestamps. Its lifetime is derived from all six dynamic deployment/recovery waits, a one-time bootstrap allowance for predecessor runtimes that expose only total active-call counts, six stop operations, four start operations, twelve bounded systemd-query windows and a 120-second recovery margin. Deploy timeouts above 120 seconds or a derived lifetime above thirty minutes are rejected before publication. Existing active, malformed or foreign markers fail closed. Expired valid markers may be removed only through the same token-, identity- and inode-bound release path.

The operator reads the marker at the FastMCP tool-call boundary. Normal calls register an identity in a lock-protected in-memory registry before the marker decision, so a call cannot slip between drain admission and accounting. Registration stores only an opaque identity, the tool name (never arguments), the execution path (`sync` worker thread or `async` event loop), a conservative effect-bearing boolean derived from the tool annotation (`readOnlyHint=true` is the only read-only case), and bounded start timestamps (wall clock and monotonic). Missing or unknown read-only metadata is effect-bearing and therefore blocks deployment. Active or invalid markers reject new calls before the registered tool function runs. Calls already admitted continue and are released by identity on completion; release is an idempotent pop so one completion can never decrement another call and duplicate callbacks cannot underflow. Effect-aware runtimes expose total, effect-bearing and read-only counts. The deployer requires the effect-bearing count to reach zero; residual explicitly read-only calls are diagnostic and may be interrupted by the service replacement without risking an unknown effect.

A sync tool stays registered for the lifetime of its executor worker, not merely of the cancellable asyncio proxy: cancellation of the awaited proxy does not release the identity, and the worker completion callback does. A queued sync worker that is cancelled before it starts releases its identity once. Async calls release in `finally` for success, exception and cancellation, and a failed executor submission releases without leaking.

## Bound deployment observer

`grabowski_runtime_deploy_schedule` may issue one short-lived random observer capability for the newly created deployment job. Only its SHA-256 digest is stored in durable job metadata. The contract also binds the exact job unit, operation `grabowski_job_status`, expected head, source-identity digest, argv digest, origin digest, issue and expiry timestamps and, when FastMCP exposes one, the requesting client identifier. The raw capability is returned only in the schedule result and cannot be recovered from job state after loss or expiry.

Before the admission marker exists, the exact capability-bound status call remains a normal counted read. This lets the deployer wait for any already-running observation before entering the drain and prevents an old capability from becoming neutral during a later deployment. Once the marker is active, the call becomes drain-neutral only with a create-only `0600` activation record in the exact job directory. That record is bound to the current marker token, job contract, head, source identity and the shorter of marker and capability lifetimes. The marker remains the only admission truth; the activation record is evidence for one observer operation and cannot admit work.

A wrong, expired, reused, foreign-job, foreign-client, head-drifted, source-drifted, argv-drifted, origin-drifted or non-allowlisted request follows the normal admission path. During an active drain it is counted and rejected. Other read-only tools, mutating tools, job logs and watchdog-generated markers receive no exemption from **new-call** admission: while the marker is active they are rejected before execution. The separate read-only classification applies only to calls that were already admitted before marker publication. Missing or malformed activation evidence also fails closed. The status response remains job-, release- and receipt-bound and does not claim deployment success before final runtime readback.

The loopback-only `/_grabowski/deployment-admission` route exposes bounded marker state and active-call diagnostics for the deployment process. The response is backward-compatible: existing fields and semantics are unchanged and only additive fields are included. In addition to `active_tool_calls`, `active_effect_bearing_tool_calls`, `active_read_only_tool_calls`, the fixed classification identifier `readOnlyHint-true-is-read-only-v1`, the fixed `active_tool_call_registry_max` capacity and `admission_gate_installed`, the response carries `oldest_active_tool_call_age_seconds` (null when no call is active), `active_tool_calls_by_kind` and bounded `active_tool_calls_by_tool_name` grouping counts (with maximum, truncation and omitted-call count), and a bounded `active_tool_calls_sample` (at most `active_tool_calls_sample_max` entries, flagged by `active_tool_calls_sample_truncated`) with opaque identity, tool name, execution kind, wall-clock start and age for each entry. The sample never contains tool arguments and is diagnostic only; it does not prove call completion or identify work beyond its bounded metadata. A nonzero `oldest_active_tool_call_age_seconds` together with stable identities, tool names and execution kinds supports correlation of repeated drain observations. Those diagnostics do not by themselves distinguish a genuine long-running call from an unreleased registry entry; both ages continue to advance until the identity is released. HTTP 404 alone means that the predecessor runtime predates this contract. Transport errors, malformed responses and other status codes are failures, not compatibility signals.

## Deployment sequence

1. Build and validate the exact source snapshot.
2. Re-read source and host-asset identity.
3. Create the source-bound admission marker and, only for an exactly bound scheduled job, its observer activation record.
4. Require two operator samples with the exact token, head and source digest and zero effect-bearing calls. A predecessor runtime without effect-aware counters falls back conservatively to zero total active calls and receives up to 300 seconds for this one bootstrap drain; effect-aware runtimes use the normal deployment timeout.
5. Require tunnel queue zero and `polled == enqueued`. Without an active admission contract, final responses must also equal enqueued commands. With the marker active and zero effect-bearing calls, a stable positive final-response gap is allowed because, once effect-bearing calls are zero, the gap can only represent already-admitted read-only work or calls already rejected by the active marker; both are no-effect work whose response may be interrupted.
6. Re-run operator and tunnel final guards immediately before service stop.
7. Stop tunnel, then operator; activate and start the replacement operator.
8. Require the replacement operator to attest the exact active marker before the tunnel starts and again immediately after tunnel startup.
9. Release the marker only after the new runtime is healthy and identity-bound; marker absence is drift, never success.

The first deployment from a predecessor runtime uses the legacy stable-counter drain only after the status route explicitly returns 404. A marker-aware predecessor that predates effect classification is also treated conservatively: all active calls must finish, but the bootstrap drain receives up to 300 seconds so long-running read-only maintenance cannot make the upgrade practically impossible. Transient transport failures are retried for up to the smaller of the deployment timeout and thirty seconds; they never establish legacy compatibility. If no explicit 404 or valid admission response becomes observable inside that bound, deployment fails closed before service stop. Every later deployment uses the admission-aware path. A predecessor may complete a scheduled deployment without an observer contract; such a deployment remains safe but cannot be polled through the drain.

## Failure and rollback

Before service stop, failure releases the exact marker and leaves the healthy runtime untouched. If observer activation fails after marker creation, the deployer releases that exact marker before returning failure. After service stop, rollback restores the previous pointer and operator, then requires that restored operator to attest the exact active marker before the tunnel may restart. A predecessor runtime without the admission contract therefore remains fail-closed with both the tunnel and restored loopback operator stopped instead of admitting work during an incomplete rollback. Only a marker-aware, identity- and readiness-verified rollback may release the marker. Missing or drifted markers are failures, not successful cleanup.

## Non-claims

The admission marker and observer capability do not authorize deployment, bypass the deployment lock, prove connector delivery, admit other work, cancel accepted commands, kill workers, or weaken review, recovery, kill-switch or privileged-execution gates. A scheduled deployment receipt or observer response still does not prove completion; exact runtime identity and health readback remain required. The active-call registry does not force-reset counters, does not expire or repair itself, and its sample list does not reveal tool arguments, request contents or secrets. Allowing a pre-existing read-only call to remain through service stop does not promise response delivery; that caller may receive a transport failure and may retry because the tool contract itself declares no effect.
